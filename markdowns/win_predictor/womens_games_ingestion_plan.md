> **Owner:** George · **Created:** 2026-08-05 · **Status:** 🟢 **ALL 6 PHASES COMPLETE for `t20w`, `odw`, AND `hndw`** — every column of this plan is now shipped. `odw`/`hndw` landed 2026-08-06/07: migration, measurement, byte-identical spec-derived refactors, generalised pooling/seeding (`POOL_SOURCE`/`SEED_SOURCE`), trained models (`odw` unpooled Brier 0.131821, `hndw` pooled-from-`t20w` Brier 0.141093, beats its own unpooled control on every held-out phase), full app/frontend wiring, and live ESPN gender routing — confirmed against a genuine live Hundred Women's fixture on ESPN's board at verification time, correctly routed to `hndw` and distinct from its men's `hnd` counterpart on the same card. > **Purpose / Strategy:** Cricsheet ships full ball-by-ball women's data (internationals, WBBL, WPL, The Hundred Women, etc.), but the pipeline **deliberately drops every non-male match at ingestion** ([cricsheet_importer.py:96-98](../../src/data_processing/cricsheet_importer.py#L96)) and every import URL is a `_male` variant. This plan adds women's cricket as **first-class women's format models** — `t20w`, `odw`, `hndw` — mirroring the existing per-format architecture exactly (the same way `hnd` was added alongside `t20`/`od`), so the win-probability / first-innings / delivery-outcome / Monte-Carlo stack all work for women's games with **no new code axis to thread** — only new `format_type` values.
> **Scope:** `cricsheet_importer.py` (female import path + gender routing) · `format_spec.py` (3 new specs) · `app.py` (model registry + startup wiring) · `regression_test.py` / `baseline_metrics.json` (women's baselines) · the scheduled import/settlement automation · optionally the live ESPN scanner + UI format selector. **The Elo, venue, state-building, and model-training code is already generic over `format_type` and needs no per-women's-format changes** — this is the whole reason the approach is cheap.
> **Cross-refs:** [[hundred_model_scoping]] / [[hundred_winprob_pooling_shipped]] (the `hnd`-as-new-format precedent this plan copies, including small-corpus train-time pooling), [[effective_game_elo_shipped]] (squad-Elo aggregation the women's models inherit for free), [[t20_player_elo_revamp]] (per-player Elo scaling the women's pools initialise fresh from).

## Starting state — 3,161 women's matches already on disk (in the wrong dirs)

Measured 2026-08-05, **before any change:** the raw dataset already contains **3,161 female-tagged YAMLs**, sitting in the **men's** directories (they pre-date the ingestion gender filter):

| Location | Female matches | Competitions |
|---|---|---|
| `data/raw/t20/` | 2,232 | `t20s` (2,035), `ssm` (197) |
| `data/raw/od/` | 921 | `odis` (598), `odms` (323) |
| `data/raw/hnd/` | 0 | — |

Current status: **parsed** into the men's `*_match_metadata.parquet` (2,232 + 921 = 3,153 female rows), but **excluded from every trained model** by the `gender == "male"` training guard, and **physically misfiled** in the men's dirs. Coverage is skewed to internationals/domestic (`t20s`/`odis`); WBBL / WPL / The Hundred Women are thin or absent — so the first import must be the **full `all_female.zip`**, not incremental. Phase 1 therefore **migrates these 3,161 files out to the women's dirs** as well as importing the full archive. This does **not** move any men's model (training already filtered them); it only shrinks the men's metadata parquet — the "men's byte-identical" gate is on the *models*, which hold.

## Read this first — why "new format codes", not a "gender feature"

The codebase is **already parameterised by a single `format_type` string** (`t20`/`od`/`hnd`). That string keys the raw directory (`data/raw/<fmt>/`), every parquet cache (`<fmt>_*.parquet`), every model artifact (`<fmt>_xgb_models.pkl`), the ball geometry ([format_spec.py](../../src/data_processing/format_spec.py)), and the model instances in [app.py](../../app.py). Nothing in Elo, venue, `build_states`, or the three trained models cares *which* format it is beyond looking up `spec(format_type)`.

That gives two candidate designs:

| Approach | What it means | Verdict |
|---|---|---|
| **A — New format codes** `t20w` / `odw` / `hndw` | Women's matches route to `data/raw/t20w/…`; each gets its own specs, parquets, Elo pools, and models — full parallel instances | ✅ **Recommended.** Zero new axis; reuses 100% of the generic pipeline; matches how `hnd` was added; Elo pools stay cleanly disjoint by construction |
| **B — Gender as a new axis** | Keep 3 format codes; thread a `gender` param through loaders, caches, Elo, models, endpoints | ❌ Invasive refactor of ~14 files, and it must **re-separate** the Elo/venue pools anyway (women's teams/players never play men's) — i.e. all of A's separation with none of A's simplicity |

> [!IMPORTANT]
> **Women's and men's must never share an Elo pool, a par score, or a training corpus.** Women's teams and players are a disjoint population, and women's scoring dynamics differ materially (lower par totals, different powerplay/death behaviour). Pooling them corrupts both team Elo (there is no shared "England" node) and the win-prob model's score-context features. Approach A enforces this **structurally** — women's matches live in separate directories, so the men's loaders (pointed at `data/raw/t20/`) literally never see them. The existing `gender == "male"` filters in [cricsheet_importer.py:372-374](../../src/data_processing/cricsheet_importer.py#L372) and `_build_second_innings_pool_states` become belt-and-suspenders (keep them).

### Scope — CONFIRMED

**`t20w` first, then `odw`, then `hndw`** (2026-08-05). `t20w` has the most data (≥2,232 already on disk + whatever the full archive adds) and the most live/betting relevance, so it validates the whole approach on the strongest corpus first. `hndw` comes last — its tiny corpus will need the same train-time pooling crutch `hnd` uses (pool `t20w` in). The plan below stays **format-agnostic**; each phase's gate is per-format keep-or-defer, exactly like the effective-Elo plan's per-format discipline. **We execute the `t20w` column first, end to end, before starting `odw`.**

## Invariants (read before touching ingestion)

> [!CAUTION]
> **The gender filter is load-bearing in two places — change ingestion routing, keep the training guard.** `classify_match()` returns `None` for `gender != "male"` ([cricsheet_importer.py:96-98](../../src/data_processing/cricsheet_importer.py#L96)) — this is the single line that currently drops all women's data. It must change to **route** women's matches to the women's format dir (not drop them). Separately, `retrain_full()` and `_build_second_innings_pool_states()` filter `meta_df["gender"] == "male"` — those guard the **men's** models against stray women's matches and must stay; the women's retrain path applies the mirror filter (`== "female"`) against the women's corpus.

> [!CAUTION]
> **Import URLs are `_male`-specific — women's data comes from a parallel `_female` archive.** Cricsheet publishes `all_female.zip` and `recently_added_<N>_female.zip` alongside the male ones. `import_recent_matches`/`import_catchup`/`import_full_archive` hardcode `_male`. Add a `gender` parameter (default `"male"` to preserve existing behaviour) so each importer can fetch the female archive, or add sibling `*_female` wrappers. The male archives do **not** contain women's matches, so this is genuinely additive — no existing import behaviour changes.

> [!CAUTION]
> **Some Cricsheet archives are NOT gender-split — competition-specific zips (e.g. "The Hundred") bundle both genders in one file.** Confirmed 2026-08-05: the men's `hnd` competition zip and a prospective "Hundred Women" pull both live under the single "The Hundred" download on Cricsheet, distinguished only by each match's own `gender:` field — unlike `all_male.zip`/`all_female.zip`, which are pre-split. This means `classify_match()` must stay the sole authority on gender **per match**, never assume "one zip = one gender" from the source file. It also means importing that combined zip will re-present the 167 men's `hnd` matches already on disk alongside the new `hndw` ones — **this is handled for free by the existing match-ID dedup** in `import_matches_from_zip_url` (`existing_hnd`/`all_existing`, checked before any write), *provided* the existing-ID scan is extended to include the women's dirs too (Phase 1 item 2) — otherwise a second run of the same zip would harmlessly-but-wastefully reprocess the male IDs it already correctly skipped once gender-routing is live (they were previously silently dropped as unclassified, not skipped-as-duplicate, so the first post-fix run is the one that must catch them via ID, not gender).

> [!CAUTION]
> **Ball geometry is identical; only the par score differs.** Women's T20 = 20×6, women's ODI = 50×6, The Hundred Women = 100 balls @ 5/over — same as the men's specs. So the new `FORMAT_SPECS` entries copy the men's geometry verbatim and change **only `default_venue_score`** (empirically ~130 for `t20w`, ~215 for `odw`, ~110 for `hndw` — measure in Phase 0, don't guess). Do **not** invent new phase edges.

> [!CAUTION]
> **Player-Elo pools initialise fresh — women's cannot seed from men's.** `hnd` warm-seeds from a frozen `t20` snapshot because they share players; **women's formats share no players with men's**, so `t20w`/`odw` start every player at the 1500 centre and build history from the women's corpus alone. Only `hndw` seeds — and it seeds from **`t20w`** (women→women), reusing the `build_hnd_seed_ratings` pattern with a `t20w` source. **Never point a women's seed at a men's snapshot.**

> [!CAUTION]
> **Small women's corpora inherit the `hnd` pooling crutch — same train-time-only, never-scored discipline.** If a women's format is too thin to train a stable win-prob model (expected for `hndw`, possibly `odw`), reuse the [[hundred_winprob_pooling_shipped]] mechanism: pool the larger women's format's second-innings states in as extra training signal (`hndw` pools `t20w`), added only at `fit()` time, never held out, never scored. Pool **within gender** — `hndw` pools `t20w`, never men's `hnd`/`t20`.

> [!CAUTION]
> **Retrain-cache trap (inherited).** `XGBWinProbabilityModel.fit()`, `FirstInningsPredictor.fit()`, `DeliveryOutcomeModel.fit()`, and the `<fmt>_*.parquet` caches all use existence/source-hash caching with no content check — a brand-new format has no stale artifacts to fight the first time, but **every re-import + retrain thereafter** must force-regenerate the women's parquets and back up the women's pkls, exactly as the men's plans require. Any ad-hoc runner needs the `if __name__ == "__main__":` guard (Windows `spawn`).

> [!CAUTION]
> **`app.py`'s model registry is hardcoded per format — going 3→6 formats is where the copy-paste hurts.** The startup block instantiates `t20_model`/`od_model`/`hnd_model` explicitly and repeats `["t20","od","hnd"]` in several loops ([app.py:41-259](../../app.py#L41)). Adding three more the same way triples the wiring and the `elif format_type == …` ladders. **Recommend refactoring the registry to a dict** (`MODELS = {fmt: XGBWinProbabilityModel(fmt) for fmt in ACTIVE_FORMATS}`) as part of Phase 4 — a small, well-contained cleanup that makes the women's formats (and any future format) a one-line addition. Keep it behind the same regression gate.

> [!NOTE]
> **Live/ESPN gender routing is a separate, deferrable concern.** `classify_espn_event()` ([format_spec.py:82](../../src/data_processing/format_spec.py#L82)) classifies by format only — it has no gender branch, so a live women's game would currently be priced by a men's model. Historical ingestion + backtesting (Phases 1-4) does **not** depend on this. Live women's support (Phase 5) is genuinely optional and can ship later; call it out but don't block the data work on it.
